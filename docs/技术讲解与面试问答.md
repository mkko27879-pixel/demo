# 论文问答 Agent：技术讲解与面试问答

这份文档只讲一件事：**这个项目里哪些地方值得讲，讲的时候怎么说**。

---

## 0. 先记住这张图

```
用户提问
   │
   ▼
┌─────────────────────────────────────┐
│ Agent（deepseek-flash + 3 个工具）  │  ← 它决定：要不要查、查几次、怎么查
│   ① search_papers   语义检索        │
│   ② list_library_papers  库清单     │
│   ③ view_page_image  页面看图       │
└─────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────┐
│ 检索层                               │
│   向量化 → Milvus 召回 → 阈值过滤    │  ← 分数低于 0.28 直接丢
└─────────────────────────────────────┘
   │
   ▼
组装上下文（片段 + 来源标记）→ 模型生成 → 答案 + 来源
```

**入库那条链路**：PDF → 文本清洗 → 切分（英文 900 / 中文 400）→ 向量化 → Milvus，元数据进 SQLite。

整条链路上，**面试里真正会被追问的点只有五个**：切分、阈值、Agent 编排、可信性、评测。下面逐个说。

---

## 1. 切分：chunk_size 为什么是 900（英文）/ 400（中文）

### 面试官会问
"文档是怎么切块的？为什么用这个大小？"

### 我们怎么做的
`app/services/text_splitter.py`：

```python
text = "".join(d.page_content for d in docs)
cjk = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")
ratio = cjk / len(text)

if ratio > 0.3:
    chunk_size, chunk_overlap = 400, 60      # 中文
else:
    chunk_size, chunk_overlap = 900, 150     # 英文
```

### 为什么

**第一个原因：`chunk_size` 是字符数，中英文的信息密度差好几倍。** 英文 900 个字符大约 150 个词，中文 900 个字符就是 900 个字。用同一个数字，中文块会塞进太多主题，检索命中率反而下降。

**第二个原因：500 太小。** 一开始统一用 500，实测块长中位数 464、最短只有 76——一个段落被切成好几块，检索回来的片段读不成完整意思。

**改大的代价（这句一定要说，它体现你知道取舍）**：块变大后向量被"摊薄"了，跨语言检索分数从 0.328 掉到 0.288，离筛选阈值 0.28 只剩 0.008 的余量。

**第三个原因：改切分参数必须全量重灌。** 库里新旧粒度混在一起，检索质量就不可预期了。

### 追问："怎么知道改完是变好还是变坏？"
看评测集的两个数：命中@1 和命中@3。改完重跑，涨了就是对的。

---

## 2. 阈值：0.28 是怎么来的

### 面试官会问
"检索回来一堆东西，你怎么保证不会拿不相关的内容胡编？"

### 我们怎么做的
`app/services/vector_store.py`：

```python
MIN_SCORE = float(os.getenv("MIN_SCORE", "0.28"))
...
return [hit for hit in hits if hit["score"] >= MIN_SCORE]
```

### 为什么

**核心认知：向量检索永远会返回"最相似的 top_k"，哪怕库里根本没有相关内容。** 实测问"今天天气怎么样"，也能拿到 0.156 的"最相似片段"。不过滤，就等于把一堆无关素材塞给模型，它会尽力编一个答案。

**0.28 是标定出来的，不是拍脑袋的。** 做法：拿 4 个相关问题测，看 top1 分数落在哪；再拿 4 个无关问题测，看它们能蹭到多少分。

| | top1 分数 |
| --- | --- |
| 相关问题（ZBL vs Lenz-Jensen / ReD 实验 / 数据集…） | 0.327 ~ 0.615 |
| 无关问题（天气 / 菜谱 / 写代码 / "Transformer 注意力机制"） | 0.156 ~ 0.251 |

分界线落在 0.25~0.33 之间，取 **0.28**，两边都留余量。注意"Transformer 注意力机制"这种**学术擦边球**是无关问题里分数最高的（0.251），因为它和论文语料有词汇重叠——这正是要留余量的原因。

### 一定要补的一句
"这个值跟语料和 embedding 模型强绑定。换成中文论文库之后，同语言匹配分数整体上移，无关问题也能蹭到 0.4，所以标定要重做。"（这不是假设，是实测：混入一篇中文论文后，两个无关问题分别漏到 0.296 和 0.422。）

## 3. Agent：和"普通 RAG"的区别在哪

### 面试官会问
"你这个和普通的 RAG 问答有什么区别？"

### 我们怎么做的
`app/routers/query.py` 里用 `create_agent` 挂了三个工具，**检索不在主流程里，而是变成模型可以调用的工具**：

| 工具 | 职责 |
| --- | --- |
| `search_papers(question, paper_id, top_k)` | 语义检索，可换关键词反复调用，可用 `paper_id` 限定某篇 |
| `list_library_papers()` | 库清单，回答"库里有哪些论文" |
| `view_page_image(paper_id, page)` | 把某页渲染成图片给多模态模型看，解决公式/表格读不出来 |

### 为什么这样设计

**普通 RAG 是固定流程**：检索一次 → 拼上下文 → 生成。三个问题：
1. 简单问题浪费一次检索，复杂问题一次不够；
2. "库里有哪些论文"这种清单问题，语义检索根本答不了（那需要查元数据）；
3. 公式和表格在 PDF 里是乱码或串行的，纯文本检索永远读不对。

**改成工具之后**，模型自己决定：要不要查、查几轮、换什么关键词。实测：
- 问"48Ca 那篇主要讲了什么" → 4 轮检索
- 问"你好" → 0 轮
- 问"库里有哪些论文" → 调 `list_library_papers`，0 轮检索

**最漂亮的一个实测现象**：中文提问时，模型第 1 轮用中文检索，第 2 轮自己改写成英文——

```
第1轮：48Ca 核态的熵和复杂度
第2轮：entropy and complexity of nuclear states in 48Ca
第3轮：Shannon entropy formula eigenvectors expansion coefficients nuclear shell model
```

跨语言检索本来是这个系统的弱项（中文问英文论文相似度只有 0.3 左右），**Agent 的多轮改写把它绕过去了**。

### 保护机制
- **轮次上限** `MAX_SEARCH_ROUNDS = 5`，防止它换着关键词无限搜。实现上有个坑：模型会在同一批里并行发多个 `tool_call`，各自都通过"还没到上限"的检查然后一起执行——所以改成**先占名额再判断**（`_reserve_round`）。
- **成本闸门** `MAX_PAGES_PER_QUERY = 2`：看一次图的 token 能顶几十次纯文本问答（实测 24.9 万 vs 6 千）。

## 4. 可信性：为什么这个系统的引用不会骗人

### 面试官会问
"你怎么保证它不编造？引用的来源可信吗？"

### 我们怎么做的（三条，按重要性）

**第一条，也是最重要的：`sources` 不解析模型写的引用标记。**

`app/routers/query.py` 的 `extract_sources()` 直接取**检索工具的真实返回值**，按 `(paper_id, chunk_id)` 去重、保留最高分、按相似度排序。

为什么这点关键：如果我把模型答案里的 `[xxx#3]` 解析出来当来源，那模型写错、漏标、编造片段号，用户看到的来源就全是假的。现在模型标不标、标得对不对，**都不影响 sources 的真实性**。

**第二条，检索为空时不给空字符串。** 工具返回的是"没有检索到相关片段，可能是库内没有收录相关内容"，而不是 `""`——否则模型会把"没搜到"理解成"库里没有"，直接回一句"未找到相关论文"。

**第三条，提示词约束 + 生成层的二次判断。**

实测案例：问"论文里用了什么深度学习模型"——
- 检索层**确实**返回了 5 条物理模型段落（0.384 > 阈值 0.28）；
- 但 agent 读完后回答"**没有找到任何关于深度学习模型的内容**"，还主动解释 `model` 在文中指的是屏蔽势模型（ZBL、Molière、Lenz-Jensen）。

**这句话一定要说**："这让我意识到，检索层的假阳不一定传导到答案——生成层会二次判断。所以我没有为了这一个假阳去加 rerank。"

### 追问："那模型编数字呢？"
"引用格式是强约束的 `[paper_id#chunk_id]`，而且 sources 里带原文片段和页码可以直接核对。要更严可以加输出校验：检查答案里的引用是否真的在 sources 里。"

## 5. 评测集：用数据做决策，而不是凭感觉

### 面试官会问
"你怎么知道改动是让效果变好了？"

### 我们怎么做的
`eval/questions.json` + `eval/run.py`：

```json
{
  "question": "论文使用了哪些数据集？",
  "expect_paper": "arxiv:2601.00597",
  "expect_keywords": ["ReD", "ARIS", "SCENE"],
  "level": "hard"
}
```

跑一轮**只走向量检索、不调大模型**，所以只花 embedding 的钱（约两分钱），输出：

```
正样本 15：命中@1 14 | 命中@3 14 | 命中@5 15 | 关键词命中 14
负样本 3：正确过滤 1
```

### 为什么这最重要

**它挡掉了我一次凭直觉的改动。** 我本来打算加 rerank（检索 top10 → 精排 top3），因为"这是 RAG 的常见优化"。但评测显示：命中@1 已经 93%，rerank 要治的那一个假阳在生成层就被消化了，**没有可测的收益**，还会打乱已经标定好的阈值。

没有评测集，我会花两个功能的时间去做一个没用的优化，还自以为"优化了检索质量"。

### 追问："题目怎么设计的？"
"两类。正样本给'期望命中的论文 + 期望出现的关键词'，负样本期望返回空。还按难度分层：简单题是论文主题的直接表述，难题用间接说法——比如不问'熵怎么算'，问'怎么衡量一个量子多体系统的混乱程度'。"

## 6. 踩过的坑（面试里最能拉开差距的部分）

面试官问"你遇到最大的困难是什么"时，别答"环境配了好久"。讲下面这两个。

### 坑一：论文重传后，旧片段还在污染检索

**现象**：重新上传同一篇论文，改小了切分参数，检索却返回已经不存在的旧内容。

**根因**：入库用的是 `upsert`，主键是 `{paper_id}_{chunk_id}`。新版本切出来的块少了，旧的那几个编号（比如 `#40`~`#55`）永远不会被覆盖，就留在库里了。

**修法**：写入前先按来源删掉整篇：`delete(filter=f'source == "{paper_id}"')`。这句还带来一个额外好处——**入库变成幂等的**，同一个 paper_id 重跑解析不会让块数翻倍。

### 坑二：流式接口把"资料原文"混进了答案（最有故事的一个）

**现象**：用户问"这篇论文主要讲了什么"，答案开头是一大段论文原文（还是英文），最后才是一句总结。

**我的错误判断**：我以为是模型在"抄资料"，于是连改三轮提示词——加"用你自己的话总结"、加输出格式示例、加"不要照搬片段开头"。全都没用。

**真因**：`agent.astream(stream_mode="messages")` **不只会推模型的 token，还会把 `ToolMessage` 一起推出来**——而工具返回的正是检索到的资料原文。我的流式代码一段段把它们拼进了答案。

**为什么我三轮都没查到**：我一直用 `TestClient` 调**非流式**接口验证，那条链路走的是 `_final_answer()`，只取最后一条 AI 消息，**本来就是干净的**。我拿干净链路的证据，去交付脏链路的代码。

**修法**：流式循环里 `if isinstance(chunk, ToolMessage): continue`。

**这个案例的价值在于**：现象（开头一段原文）长得太像"模型抄资料"，而根因在接口层。教训是 **验证必须走用户实际使用的那条链路**。

### 坑三：参考文献污染检索

检索"统计方法比较模型"时，一条参考文献（Zelevinsky 1995 的文献条目）排到了第一。参考文献术语密集、期刊缩写满天飞，特别容易和抽象问句匹配上，但它几乎不可能是答案来源。修法是在清洗阶段整段丢弃。

**修复过程也有个坑**：第一次改完指标一点没动——因为我的清洗顺序写反了，先把段内换行合并成了空格，之后 "References" 标题和 `[12]` 就不在行首，规则全部失效。调整顺序后块数从 35/49/22 降到 33/45/21，说明真的生效了。

## 7. 自测：这 10 个问题你能秒答吗

对着镜子说，卡住的回去看对应章节。

1. chunk_size 为什么中英文不一样？改大的代价是什么？
2. 0.28 这个数是怎么定出来的？为什么不能照搬到中文语料？
3. 你这个 Agent 和普通 RAG 的区别？举一个实测的例子。
4. 为什么中文提问能查到英文论文？
5. sources 为什么不用模型写的引用标记？
6. 检索返回了不相关内容，为什么答案还是对的？
7. 为什么最终没加 rerank？靠什么判断的？
8. `insert_chunks` 里为什么要有 `delete`？
9. 流式接口那个 bug，根因是什么？为什么前面三轮排查走偏了？
10. 换成 10 万篇论文，这个架构哪里先崩？

第 10 题现在可以这样答：**先崩的不是向量检索**（400 万向量 Milvus 单机撑得住），而是入库流水线——单进程 `BackgroundTasks`、没有队列、任务不持久化，服务重启任务就丢；其次是 embedding 成本和元数据的 SQLite 单文件锁。

## 8. 如果只记三句话

1. **参数不是拍脑袋来的**：切分按语料密度自适应，阈值按分数分布标定，都留了实测数据。
2. **可信性靠设计不靠模型**：来源直接取工具返回值，不解析模型输出；检索不到就明确说没有。
3. **用评测集挡掉凭直觉的优化**：rerank 该不该做，是数据说了算，不是"RAG 通常这么做"。
